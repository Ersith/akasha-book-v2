## 1. 漏召率复盘（失败回查纪律的真实有效性）

**数据**：失败回合 **59**；失败前**已查库 9 / 未查库 50**（其中**事后才查 7**）⇒ **漏召率 84.7%**；事后补救率约 12%。

**结论（三层，别混成一句"纪律没用"）**
1. **结构层**：一半以上失败**本来就不该靠记忆避免**——`web_fetch`（网络）、`edit` 的字符串匹配失配等，属工具/环境面。**用同一个率去衡量"记忆有效性"是错的**，必须按**可预防性**分层统计（下一条）。
2. **可预防层（真问题）**：**`pwsh`×13 + `edit`×29 里有相当比例是"我们早就写进库的坑"**——引号/转义、单引号内嵌单引号、行号核对、编码。库里（canon + orphan + mirror）**有对应条目**，但**它们没在动手前被调用**：这正是**「称呼漂移」的同族病**——规则躺在库里，**执行点没有接线**。
3. **观察层**：事后补查 7 次说明"回查提示"**有**效力，只是**太晚**（它是失败后的提示，不是动手前的）。

**漏召率时间序列（2026-10-10 分析）**：按天 10-06 82% → 10-07 74% → 10-08 100% → 10-09 83% → 10-10 100%；**自上线首日即高位、无"某点之后抬升"**（按小时亦零散，无聚集）。失败**绝对数**反而下降（17→19→12→6→5，约 3×）。日样本仅 5–19 条 ⇒ **日间差在噪声内，不判 breakpoint**（不编造趋势）。
**度量有效性缺口（自认）**：识别"召回动作"的口径只认 `mcp__akasha__*` 只读工具 + 被标注的 akasha CLI 子命令；**经 `dsh_wsl` 的 CLI 查库在 2026-10-10 之前不计入召回**（当日才补），其它未识别路径同理 ⇒ **真实漏召率可能低于 84.7%**。
**新类别：矛盾式漏召（用户观察，2026-10-10）**：日常几乎无"明显遗忘"；唯一显著实例是**同一会话内自相矛盾**（npm 暂存事实：先经用户截图实证"队列为空"，后被 E409 措辞推翻）。⇒ 冲突裁决顺序钉死：**用户实证 > 库内记录 > 工具输出措辞**；"状态性事实"（发布/审核/文件/配置/版本/开关）**断言前必查**。

**C2 v2（2026-10-10，外部评审建议）**：判定改**显式"工具→坑条目"映射表**（`RECALL_TRAP_MAP`：pwsh/bash/edit/write/read/grep/dsh_wsl/codex_exec/apply_patch → 库内坑条目 id），并**校验条目存在**（退役/更名即自动失效，不悬空）；结构性工具（web_fetch/web_search）永不入表。替换 v1 的"按工具名强命中"（那条会**仅提到该工具**也算命中）。
**A/B 对照实验设计**：见 [`docs/ab-experiment-design.md`](ab-experiment-design.md)（双臂交替 + 20 题配对 + 盲评；H1 同坑复发率 / H2 失败复现率 / H3 不可逆前查库率 / H4 任务分 / **H5 矛盾式漏召**；过程指标与结果指标分栏；负结果同需入 canon）。

**口径修正（2026-10-10，可预防性测试第 1 步当场发现）**：原「失败 59 / 未查库 50 / 84.7% / 可预防 44-40-90.9%」**含 11 条门控拒绝**（守卫按设计工作，非任务失败）⇒ 修正为 **失败 49 · 未查库 41 · 83.7% · 可预防 34-31-91.2%**；回归断言入核心套件（140/140）。*教训：度量分母也要"防自家组件灌水"。*

**C2 已落地（2026-10-10，外部评审指定的第一优先）**：`metrics` 的召回信号扩为**分层口径**——
- 原始：失败回合 **59** · 未查库 **50（84.7%）** · 事后才查 7；
- **可预防口径**：库内有同类坑的失败 **44** 次，其中漏召 **40** 次 ⇒ **可预防漏召率 90.9%**；
- 按工具 top3：`edit×24`（未查 22 / 可预防漏 22）· `web_fetch×12`（未查 7，**结构性豁免**）· `pwsh×10`（未查 9 / 可预防漏 9）；
- 判定（`recallToolTraps()`）：工具名在库内有**强命中**即视为"有坑可查"；**结构性工具（web_fetch / web_search）永久豁免**（网络/环境类，任何库都预防不了）；
- **口径局限（自认）**：v1 是"按工具名查强命中"，会把**仅仅提到该工具**的条目也算命中（偏宽）；下一步可换"工具→坑条目"的显式映射表。分母口径 = **库内有坑的失败数**（44），不是全部失败（59）。

**候选对策（不实现，登记待评估；须测试期解冻后另行裁定）**
- **C1｜易错点前置提示**：把"某工具的已知坑"在**首次使用该工具当回合**注入（类似称呼行的执行点思路：`akasha:tool-trap` 行，按 tool 名匹配 canon/orphan 的 `traps` 标签）。成本：一行 context + 一个标签约定。
- **C2｜分层统计**：`metrics` 的漏召率**按工具分列**，并标注"该工具是否有可预防条目"⇒ 得到一个**可预防漏召率**（分母换成"本可预防的失败回合"）。这是**度量修正**，不是新功能，优先级高于 C1（没有正确分母，C1 的收益无法验收）。
- **C3｜动手前一句话**：把"相关主题先 brief"从软协议升级为**每回合脉冲行的固定半句**（现脉冲行只报库况计数，不提纪律）。

## 5. 解冻闸 · 防误读 · 路由边界（2026-10-10 定）

**解冻闸（四项全绿才谈解冻；缺一不可）**
1. **可预防漏召**有**机检定义**（＝失败前未查库 ∧ 库里同主题强命中/同类工具坑）并把该率降到双方约定的阈值；
2. **开/关对照跑完**（同一任务电池，开阿卡夏 vs 关阿卡夏；看**失败复现率 / 不可逆操作前查库率 / 同坑复发率**，不看调用次数）；
3. **商城过审**（五件人工审核通过）；
4. **sleep 1.5.4 上架 npm**（当前状态：**已暂存，待 2FA 批准**）。

**防误读（写进台账与卷宗）**：`成功率 98%`、`引用命中 124`、`轻查动作率 3.7%` **都是过程指标**，**不能**被读成"记忆有效"或"任务更好"；能装（E3/商城预检）也不等于长期有用。

**路由边界补充**（三套记忆分工的漏点）：**「我对他人的偏好」→ OpenViking**；**「我对某类人的判断规则」→ 阿卡夏**；灰色地带（既像偏好又像纪律）**以"有没有可复用的判断规则"为准**，有则落阿卡夏并在 `ref` 里指向 OpenViking 的同题条目。
