# 观察口径与方法：C1/C3 基线期 → 观察期

> 目的：在**不做 A/B** 的前提下，用同口径过程指标回答一个问题——**"动手前先查"这件事，有没有真的发生得更多、坑有没有踩得更少**。
> 配套脚本：`akasha/tools/observe.mjs`（只读；不改任何数据）。

## 1. 窗口定义（写死）

| 窗口 | 区间 | 说明 |
|---|---|---|
| **基线期** | C1 上线前（≈ 2026-10-06 → 2026-10-10） | 无 `preflight` / `stateful-reminder` 事件 |
| **观察期** | C1/C3 上线后 **5–7 天**（2026-10-10 → 10-17） | 保持同口径 |

## 2. 五个指标（定义写死，防事后解释）

| # | 指标 | 定义 | 数据源 |
|---|---|---|---|
| M1 | **C1 触发数** | `hooks` 里 `kind=preflight` 的条数 | hooks.jsonl |
| M2 | **提示后同工具再失败** | 某条 preflight 之后 **30 分钟内**同工具再出现 `ok:false`（**提示无效的粗代理**，不等于"提示没用"） | hooks.jsonl |
| M3 | **C3 触发数** | `kind=stateful-reminder` 条数 | hooks.jsonl |
| M4 | **同坑失败**（**回合级 / 会话级 分列**，Claude 要求） | 落在 `RECALL_TRAP_MAP` 覆盖工具上的失败：逐次计（回合级）／同一会话只计一次（会话级） | hooks.jsonl |
| M5 | **可预防漏召率** | `recallSignals` 的 preventable 口径：库内有坑条目的失败里，失败前未查库的占比（**回合级**；会话级另列） | hooks.jsonl + lib.mjs |
| M6 | **H5 候选（矛盾式漏召）** | 会话层 `gist` 命中「更正 / 恰恰相反 / 我错了 / 已纠正 / 改口」等更正语条数（**候选，须人工复核**） | data/session.jsonl |

## 3. 怎么跑

```powershell
cd <AKASHA_DIR>
node tools\observe.mjs --since 2026-10-10                    # 单窗口
node tools\observe.mjs --base 2026-10-06:2026-10-09 --obs 2026-10-13:2026-10-17   # 两窗口对照
node tools\observe.mjs --since 2026-10-10 --json             # 附 JSON 摘要（可存档）
```

## 4. 判定规则（**先注册，后看数**）

- **主判据**：观察期相对基线期，**M4 会话级同坑失败下降** ∧ **M5 可预防漏召率下降**（方向一致才算"有效"）；
- **参考阈值**（源自"可容忍漏掉几次"）：可预防漏召率**第一期目标 ≤15%**（基线 83–91%）；
- **反指标**：M1+M3 触发数**暴涨**（> 每回合 1 条量级）⇒ 判"提示变噪声"，需收紧；
- **负结果同样入库**：7 天后若**无方向性变化**，在 canon 里写"**无效**"并记录当期口径（不做美化）；
- **不作弊条款**（沿用）：不得为提升指标而增加非必要查库。

## 5. 已知局限（写给将来读它的人）

1. **M2 只是粗代理**——"提示后仍失败"可能是任务本身难，不代表提示无用；真正看 M4/M5 的趋势；
2. **M6 是词组命中**——只当候选，**必须人工复核**（我们吃过"机器初筛真阳性 0"的教训）；
3. **样本量小**：每天 2–3 个会话、8–13 次失败量级 ⇒ **只看趋势，不谈统计显著性**；
4. **两期任务构成不同**（不是 A/B）⇒ **不得作因果结论**，只能说"同口径下是否改善"；
5. 基线期与观察期的**库规模在变**（`RECALL_TRAP_MAP` 11 工具、坑条目在增）⇒ 复算时同时记录库版本。
